# Phase 2 — Evidence-Based Verification of Critical Audit Findings

I have completed an initial read-only audit of the Punjab Industries Survey App. The previous report identified six important findings that require deeper verification.

Your task is to investigate these findings against the actual current workspace. Do not modify files, apply fixes, install packages, or execute database mutations.

## Rules

1. Reopen the actual source files. Do not rely on the previous report as proof.
2. Cite exact file paths, line numbers, and relevant code snippets.
3. Trace each finding through the full execution path.
4. Distinguish confirmed defects from conditional risks and false positives.
5. Inspect all relevant SQL schema files, seed scripts, migrations, entities, controllers, services, and frontend components.
6. Do not expose credentials or secret values.
7. If a finding depends on the live database or production configuration, explain what cannot be verified locally.

## Finding 1 — JWT Secret and Authentication

Inspect:
- `backend/src/app.module.ts`
- `backend/src/common/guards/rbac.guard.ts`
- `backend/src/bll/services/auth.service.ts`
- `backend/src/main.ts`

Verify:
- Whether a hard-coded JWT fallback exists.
- Whether an empty or missing `JWT_SECRET` allows startup.
- Whether token signing and verification use the same fallback.
- Whether the guard validates expiration and signature.
- Whether issuer and audience checks are configured.
- Whether user activation status and permission changes are checked after login.
- Whether any alternative revocation mechanism exists.

Provide a precise exploitability assessment and the minimum safe remediation.

Do not generate or attempt forged tokens.

## Finding 2 — Duplicate-Flag Schema Mismatch

- `backend/src/bll/services/survey-response-writer.ts`
- `database/schema.sql`
- All SQL files that create or alter `duplicate_flags`

Trace the duplicate-detection path from the PostGIS query through reason construction, entity persistence, and transaction commit.

Verify:
- The exact values written into the `reason` column.
- The column type and any CHECK constraints.
- Whether later migrations change those constraints.
- Whether TypeORM mappings match the SQL schema.
- Whether an exception rolls back the response and industrial-unit creation.
- Whether the service returns a failed result or a duplicate-flagged result.

Show the exact conflicting values and determine whether the issue is confirmed against the checked-in schema.

## Finding 5 — Offline Data Ownership Across Logout

Inspect:
- `frontend/src/context/AuthContext.tsx`
- `frontend/src/lib/db.ts`
- `frontend/src/pages/SurveyPage.tsx`
- `frontend/src/pages/SyncPage.tsx`
- `frontend/src/lib/api.ts`
- `backend/src/controllers/sync.controller.ts`
- `backend/src/bll/services/sync.service.ts`

Trace the lifecycle of a pending response when:
1. User A creates a survey offline.
2. User A logs out.
3. User B logs in on the same device.
4. User B synchronizes pending responses.

Determine whether responses are associated with their creator in IndexedDB, whether the backend trusts client-supplied ownership, and how the authenticated user ID is assigned.

Inspect account switching, HTTP 401 handling, failed synchronization, and response status transitions.

Recommend a safe data-ownership design that preserves unsynchronized work while preventing accidental cross-account submission. Do not clear IndexedDB or simulate this against real data.

Trace the photo from file selection through browser serialization, IndexedDB, the sync request, backend validation, database persistence, and any retrieval/display functionality.

Determine whether the photo is:

- Written to a file/object-storage location.

Do not upload files to any external service.
